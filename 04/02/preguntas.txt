| amazon-ssm-agent | 1029 | root | 2.2 | Es el agente de AWS Systems Manager. Permite gestionar la instancia de forma remota (por ejemplo, Session Manager) sin depender de abrir el puerto 22. Usa alrededor de 20 MB de memoria residente. |

También se observa snapd (PID 667), el gestor de paquetes snap, que en esta
muestra es el proceso con mayor memoria residente (~43 MB). No es necesario

de AWS/Ubuntu además del sistema base.

== Análisis de logs ==

journalctl -n 30 mostró la inicialización de la sesión de usuario, tareas de
cron cada cinco minutos (debian-sa1, parte de sysstat), la ejecución de
sysstat-collect.service y el registro del propio sudo. Eso indica que el
sistema está sano y que los servicios programados se están ejecutando.

systemctl status ssh mostró el servicio activo (running), con Main PID 1153.
El servicio aparece como "disabled" pero es activado por ssh.socket
(TriggeredBy: ssh.socket), lo cual es normal en Ubuntu 24.04. También tiene
un drop-in de EC2 Instance Connect y el log confirma el acceso con clave
pública:

    Accepted publickey for ubuntu from 191.95.162.60 port 9392 ssh2:
    RSA SHA256:...

Eso confirma que el acceso fue por SSH con key pair, no por contraseña.

== Observaciones técnicas ==

1. El comando pgrep -a systemd-journald falla porque pgrep busca nombres de
   proceso de máximo 15 caracteres y "systemd-journald" tiene 16. No es un
   error del sistema; la forma correcta es:

       pgrep -af systemd-journald

   o:

       ps -C systemd-journald -o pid,user,comm,args

2. df muestra /dev/root y findmnt muestra /dev/nvme0n1p1 para el mismo
   filesystem raíz. /dev/root es un alias; el dispositivo real es
   /dev/nvme0n1p1. Ambos apuntan al mismo ext4 montado en /.

3. /boot está en otra partición (/dev/nvme0n1p16, 881 MB). Por eso el script
   con argumento reporta un filesystem distinto al ejecutarlo con /boot.

4. El script system_info.sh automatiza la recolección de hostname, usuario,
   fecha, uptime, disco, memoria y procesos. Con el argumento opcional puede
   inspeccionar el filesystem de cualquier ruta:

       ./scripts/system_info.sh /var/log
       ./scripts/system_info.sh /boot

== Conclusión ==

EC2 entrega la infraestructura (cómputo, red, almacenamiento), pero la
administración del sistema operativo sigue siendo responsabilidad del
usuario: revisar procesos, leer logs, gestionar permisos, crear scripts y
monitorear recursos. En este taller se comprobó que la instancia tiene
recursos suficientes para el laboratorio, que SSH funciona con clave pública
y que systemd/journald permiten observar el estado del servidor. El script
system_info.sh deja una base reutilizable para automatizar la recolección de
métricas antes de pasar a Docker en el siguiente taller.
